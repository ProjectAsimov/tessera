# App bundles and Play App Signing

Sources (fetched 2026-10-07): https://developer.android.com/guide/app-bundle ("About Android App Bundles"); https://play.google/play-app-signing-terms/ ("Play App Signing Terms of Service", effective 1 Aug 2021); plus Play Console Help "Use Play App Signing" (answer 9842756 - this is the page behind the data-safety URL you listed), Android versioning docs, and Play "Prepare and roll out a release" (answer 9859348).
Paraphrased from a summarising fetch; the signing terms page was summarised thinly (see gaps).

## Android App Bundle (AAB)
- An AAB is a publishing format containing all compiled code and resources, with APK generation and signing deferred to Google Play. Play generates and serves optimised APKs per device configuration, so users download only what they need.
- Requirement: since August 2021 new apps must be published with an Android App Bundle. TV apps (new and existing) must be bundles since June 2023.
- Structure: a base module (core functionality), optional feature modules (conditional, on-demand, install-time, instant), and asset packs (games, Play Asset Delivery). A TWA wrapper is a single base module.
- Size: the compressed download limit is 4 GB (initial install = base APK + config APKs, and each later on-demand feature download). Asset packs have separate limits. New apps over 200 MB are supported via Play Feature Delivery or Play Asset Delivery (per the page's August 2021 note). A TWA is a few MB, so this is irrelevant for Tessera.
- Not supported: APK expansion (.obb) files.
- What Play generates: configuration APKs split by CPU architecture, screen density, language, API level and device capability. Keep `enableSplit = true` for each split type. Tools that dynamically modify the resource table should be disabled when building bundles.
- Updates: users receive updates through Play, which ensures all required split components are installed. Partial/sideloaded installs missing splits fail on Google-certified devices and Android 10+.
- Build config: do not set conflicting build settings between base and feature modules (e.g. debuggable differing).
- Build and upload a signed bundle from Android Studio or Gradle (`bundleRelease`), then upload in Play Console.

## versionCode rules
- `versionCode` is a positive integer; maximum 2,100,000,000; must increase monotonically with each release; Play will not accept a `versionCode` that was previously uploaded to the app. Users never see it; `versionName` is the display string.
- Define it in Gradle (Gradle values override the manifest). For this repo that is android/app/build.gradle; the existing store/twa-manifest.json `appVersionCode` must match if Bubblewrap regenerates the project.
- Other upload expectations (target API, 64-bit, signing) are not stated on the pages fetched; see content-policy.md (Target API Level) and check Play Console's upload errors. The "Prepare and roll out a release" page does not list technical upload specs.

## Play App Signing - how it works (Play Console Help)
- Two keys: the **upload key** (kept by the developer in a Java keystore; RSA 2048 bits or more) authenticates who uploads bundles; the **app signing key** is held by Google on its infrastructure and signs the APKs delivered to users. New apps get Google-generated signing keys (the page mentions hybrid post-quantum signing for new apps).
- Because Google signs the final APK, third-party registrations (Google Maps, OAuth, Facebook Login, etc.) must use the **app signing key's** SHA-1/SHA-256 fingerprints from Play Console (Release > Setup > App signing), not the upload key's.
- Recovery: if the upload key is lost or compromised, generate a new upload key, export its certificate as PEM, and request an upload key reset in Play Console. If the app signing key is compromised, request an upgrade/replacement via Play Console (the page describes an annual upgrade request; Google generates the replacement).
- Google adds source/stamp metadata (com.android.stamp.source and com.android.stamp.type) to the manifest for traceability.

## Play App Signing Terms of Service - plain English
- Scope: applies to developers who enrol in the service, alongside the Developer Distribution Agreement and Developer Program Policies. If the terms conflict with the Agreement, these terms govern the service.
- Key custody: you either give Google your chosen app signing key(s) or have Google generate and store a new one. "It will not be possible to retrieve Your app signing key once it is provided to or generated by Google." Google may keep a backup copy indefinitely for disaster recovery.
- Licence you grant: a non-exclusive licence to (1) use the Android App Bundle you provide to generate APKs and (2) modify the app APKs to optimise performance, security and/or size; modifications will not change the app's purpose.
- Developer rights/obligations: you accept the terms by enrolling; you may download APKs for review and for distribution of signed versions yourself.
- Changes and termination: if you disagree with modifications to the terms you may stop using the service, which is your sole and exclusive remedy.
- Gaps: the fetched text did not describe key reset procedures or certificate use. Those come from the Play Console help page above. Do not state more about Google's liability or warranty without re-reading the full terms.

## Digital Asset Links and the signing certificate (Tessera TWA)
- A TWA proves ownership of its web origin through /.well-known/assetlinks.json on the PWA domain, containing the SHA-256 fingerprint of the certificate that signs the installed APK.
- With Play App Signing, the installed APK is signed by the Play app signing key, so assetlinks.json must list the **app signing key** SHA-256 from Play Console. Also keep the upload/debug key fingerprint listed if you want sideloaded or locally built APKs to verify. Missing/wrong fingerprint makes the TWA show the browser URL bar (verification failure).
- The developer-docs assetlinks page could not be fetched (HTTP 404 on the URL tried); this paragraph is standard TWA practice and the Play help statement about registering the app signing key fingerprint, not a quote from a fetched Digital Asset Links page. Verify against Chrome TWA docs.
- Repo files involved: android/assetlinks.json, android/twa-manifest.json, and the deployed https://<pwa-domain>/.well-known/assetlinks.json.

## Checklist items
- [ ] Release artifact is an .aab (not .apk) built with `bundleRelease`.
- [ ] `versionCode` is higher than any previously uploaded build and below 2,100,000,000; `versionName` updated.
- [ ] Play App Signing is enrolled for the app; the upload keystore is backed up outside the repo and its password stored securely.
- [ ] Upload key certificate (not private key) is the only thing referenced in repo docs; private keystore files are gitignored.
- [ ] Play Console app signing key SHA-256 is copied into assetlinks.json and the file is served from the live domain without redirects.
- [ ] Google OAuth client for Android (if used) is registered with the app signing key SHA-1/SHA-256, not just the upload key.
- [ ] TWA opens without a URL bar when installed from the Play internal/closed test (confirms Digital Asset Links verification).
- [ ] Upload key reset procedure (generate new key, export PEM, request reset) is documented in the wrapper README.
- [ ] Team understands Google holds the signing key irrecoverably and may optimise APKs per the terms.
